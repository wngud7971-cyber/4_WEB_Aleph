# 김치 프리미엄 — 매일 궁금한 값 하나 (Aleph T04)

업비트(국내) 가격과 CoinGecko(해외) 가격을 Frankfurter(ECB) 환율로 정규화해 비교한
"김치 프리미엄"을 **비트코인·이더리움·리플 3종목**으로 보여주는 정적 웹사이트입니다.
세 API 모두 **키·로그인 없이** 호출 가능하며, 종목이 늘어도 각 API를 한 번씩만 호출합니다
(업비트 `markets=KRW-BTC,KRW-ETH,KRW-XRP`, CoinGecko `ids=bitcoin,ethereum,ripple` — 여전히 실외부 호출 3개).

## 배포 방법 (5분)

1. 이 폴더 전체를 새 GitHub 저장소에 push 합니다 (public repo로 만들어야 로그인 없이 열립니다).
2. 저장소 Settings → Pages → Source를 `main` 브랜치 `/ (root)`로 설정합니다.
   → `https://<계정명>.github.io/<저장소명>/` 형태의 URL이 생깁니다. 이 URL을 제출하세요.
3. Settings → Actions → General에서 "Workflow permissions"를 **Read and write**로 바꿉니다.
   (`.github/workflows/daily-fetch.yml`이 매일 `data/records.json`에 커밋하기 위해 필요합니다.
   여기 쓰이는 `GITHUB_TOKEN`은 GitHub가 자동으로 주입하는 값이라 코드/화면 어디에도 노출되지 않습니다 — 별도 비밀키 관리가 필요 없습니다.)
4. Actions 탭 → "Daily kimchi premium fetch" → "Run workflow"로 한 번 수동 실행해서 오늘자 기록을 만들어 두세요.
   그 다음 날 자동 실행되면 두 번째 실제 날짜 기록이 쌓입니다 (T04-C22 요건).

## 짧은 확인 방법 (T04-C27)

1. **어디로 가나요**: 배포된 GitHub Pages URL을 새 시크릿 창에서 엽니다.
2. **3단계 이내 무엇을 하나요**: (1) 페이지 로드 → 상단 값 자동 조회 (2) "원자료 상세" 표에서 3개 출처 확인 (3) "일별 기록" 표에서 날짜별 한 줄씩 쌓였는지 확인.
3. **무엇이 보이면 통과인가요**: 상단에 `%` 값, 상태 배지 `fresh · error_code: none`, 조회 시각·기준 시간대(Asia/Seoul)가 보이고, 원자료 표 3행 모두 값·단위·출처 링크·출처 시각이 채워져 있으면 통과. (페이지는 로드 시 한 번만 자동 조회하며, 상태 배지 옆 "↻ 새로고침" 버튼으로 즉시 재조회할 수 있습니다 — 서버 폴링은 없음.)
4. **안 될 때 무엇이 보이나요**: 하단 "검수용 · 합성 실패 재생" 패널의 버튼(느린 응답/401/403/호출 제한/오프라인/응답 형식 변경)을 누르면 상태 배지가 `stale` 또는 `error · error_code: ...`로 바뀌고, 마지막 정상값은 "(지연됨)" 표시와 함께 그대로 남습니다. "다시 시도"를 누르면 `fresh · error_code: none`으로 복귀하고 일별 기록에 다음 날짜 한 줄이 추가됩니다.

## 설계 판단: 수수료, 다중 허브, 그래프

- **거래소 수수료**: 프리미엄 계산 자체에는 수수료를 반영하지 않습니다 (업계에서 통용되는 "김치 프리미엄" 정의와 동일 — 원시 가격 괴리율). 대신 화면에 "가정 왕복 수수료(%)" 입력창을 두어, 입력한 값만큼 뺀 참고치를 별도로 보여줍니다. 실제 수수료는 거래소·회원 등급·네트워크 전송비(고정액이라 %로 환산 불가)에 따라 달라서 하나의 숫자로 강제 반영하면 오히려 오해를 줄 수 있다고 판단했습니다.
- **다중 종목**: 비트코인·이더리움·리플 3종목을 탭으로 전환해서 상세를 보고, "종목별 프리미엄 한눈에" 표로는 항상 3종목을 동시에 비교할 수 있습니다. 알트코인(특히 리플)은 유동성이 낮아 프리미엄이 비트코인보다 훨씬 크게(또는 반대로) 벌어지는 경우가 흔해서, 비교 자체가 의미 있는 데이터가 됩니다. `data/records.json`의 하루 한 줄 기록에는 3종목 값이 모두 들어가므로 "하루 한 줄" 요건(T04-C20)은 그대로 유지됩니다.
- **다중 허브 비교**: CoinGecko 한 번의 호출(`vs_currencies=usd,eur,gbp,jpy`)과 Frankfurter 한 번의 호출(`base=EUR&symbols=USD,GBP,JPY,KRW`)만으로 뉴욕(USD)·프랑크푸르트(EUR)·런던(GBP)·도쿄(JPY) 4개 허브를 비교합니다. API 호출 수는 늘지 않았습니다(여전히 3개: 업비트/CoinGecko/Frankfurter). 대표(헤드라인) 프리미엄%는 관행대로 USD 기준을 사용합니다.
- **상하이(CNY) 제외**: 중국은 자국 내 암호화폐 거래를 금지하고 있어, 공식 환율로 환산해도 실제 거래 가능한 가격이 아니라 부정확한 참고치만 될 뿐입니다. "실제 조회 화면 값이 원자료와 일치해야 한다"는 과제 기준(T04-C10)에 맞지 않는다고 판단해 처음부터 제외했습니다.
- **그래프**: 별도 차트 라이브러리 없이 순수 SVG로 그렸습니다 (오프라인/단일 파일 유지 목적). 기록이 2건 이상일 때부터 표시됩니다.

## 알아둘 점 / 직접 판단한 부분

- **T04-RECOVER-D2**: 과제 안내에 이 asset의 정확한 형식이 없어서, `fixtures/T04-RECOVER-D2.json`을 직접 정의했습니다
  (합성 시험값임을 파일 안에 명시). 채점 스크립트가 특정 형식을 기대한다면 이 파일 구조를 맞춰 조정하세요.
- **"느린 응답" 재생**: 실제로 몇 초씩 기다리게 하는 대신 즉시 timeout 상태로 전환되게 만들었습니다 — 실제 환경에서는
  타임아웃 임계값(예: 8초, `app.js`의 `timeoutMs`)을 넘겨야 발생합니다.
- **개인정보 없음**: 다루는 값은 시세·환율뿐이며 로그인/사용자 계정을 두지 않았습니다 (T04-C25).

## 제출문 (T04-C28)

아래는 작성 예시이며, 실제로 어떤 부분을 그대로 쓰고 어떤 부분을 바꿨는지에 맞게 스스로 채워 넣어야
채점 취지(AI 위임 vs 본인 판단 구분)에 맞습니다.

- **① AI에게 맡긴 일**: 3개 공개 API 연동 코드, 정적 페이지 마크업/스타일, GitHub Actions 워크플로 초안 작성.
- **② 학생이 직접 판단한 일**: (예) 주제를 "비트코인 단순 가격"에서 "김치 프리미엄"으로 변경 결정, 색상 규칙(양의 프리미엄=빨강)이 국내 관행에 맞는지 확인, `T04-RECOVER-D2` 형식을 직접 정의.
- **③ AI 제안을 따르지 않은 일**:
  - 처음 제안받은 "미세먼지(공공데이터)" 안은 서버에 키를 숨겨야 해서 채택하지 않음 — 이유: 별도 서버 배포·운영 부담이 과제 범위를 넘는다고 판단.
  - AI가 해외 허브 비교에 상하이(CNY)를 포함해 제안했으나 채택하지 않음 — 이유: 중국은 자국 내 암호화폐 거래를 금지하고 있어 공식 환율로 환산해도 실제 거래 가능한 가격이 아니고, "실제 조회 화면 값이 원자료와 일치해야 한다"는 과제 기준(T04-C10)에 맞지 않는 부정확한 값이라고 판단.

## 파일 구조

```
index.html               화면 전체 (마크업 + 스타일 + 로직을 한 파일에 인라인)
data/records.json        일별 기록 (GitHub Actions가 매일 갱신)
scripts/fetch_daily.mjs  Actions가 실행하는 조회·계산·기록 스크립트
fixtures/T04-RECOVER-D2.json  합성 복구 재생용 공개 자산
.github/workflows/daily-fetch.yml  매일 자동 실행 설정
```

`index.html`은 단일 파일이지만, "일별 기록"(하루 한 줄씩 실제로 쌓이는 값)은 화면 파일 하나만으로는
만들 수 없어서 `data/records.json`을 갱신하는 `scripts/fetch_daily.mjs` + 매일 실행되는
`.github/workflows/daily-fetch.yml`은 별도로 둡니다. 자세한 이유는 대화 참고.
